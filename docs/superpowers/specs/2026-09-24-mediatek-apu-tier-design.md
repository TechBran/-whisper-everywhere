# The MediaTek APU tier — design

**Status:** design for review, 2026-09-24. Owner ruling the same day: *"Build the tier. Yes."*, plus *"a version
checker there to make sure we're hitting the right chip for the driver."* The owner is reading MediaTek's
NeuroPilot Express SDK licence themself; nothing ships to Play before that is accepted.

**What this is:** `npu-turbo` — the app's fastest local tier, large-v3-turbo on an AI chip — on MediaTek's APU,
starting with the Galaxy Tab S10+/S10 Ultra (MT6989) and compiled for the Tab S11/S11 Ultra (MT6991). Same tier
id, same card, same commit cadence, same policies as the Qualcomm tier; a second vendor behind the seam, not a
second tier.

**What was measured today (`docs/measurements/2026-09-24-tab-apu-turbo-encoder.md`):** the turbo encoder on
the Tab S10+'s APU: 1,713–1,783 ms per 30 s window, flat over 120 runs; the decoder step 22.8–24.3 ms per token;
real speech through both, word-perfect; RSS ~4 GB for the pair; process cold start 8.3 s for the first model
(5.0 s of it one binder timeout) and 0.9 s for the second. A 20-token commit ≈ 2.24 s. The S23 was admitted
to this tier at 2.47 s encode.

## 1. Goals and non-goals

Goals
- The Tab S10+ class runs `npu-turbo` from the Play build with the existing bubble, cadence, sentence, speaker,
  language and fallback behaviour unchanged.
- One census, one gate shape, one pack pipeline, one backend policy body. Vendor differences live in an engine
  seam and in per-family data, nowhere else.
- A driver check that refuses the tier, loudly and before any model loads, when the device's Neuron driver is
  not the one the bytecode was compiled against.
- Every number the tier depends on is measured on the owner's tablet and written down; the probe app's runs are
  the acceptance references.

Non-goals
- `npu` (Whisper Small) on MediaTek. Owner: *"Don't necessarily need small for the tablets."* The families offer
  turbo only, the way `qcs8550` shipped turbo-only first (commit 7494e4a: hide, do not delete).
- Phones. MT6989/MT6991 phones (vivo, OPPO, Xiaomi Dimensity 9300/9400) are matched by the same strings and will
  get the packs, but the ship gate is the Samsung tablets the tier was measured on; a phone ROM whose driver
  fails the check falls back to the CPU tier exactly like an unsupported Qualcomm part does today.
- Integer quantisation on the APU (per-channel int is rejected by the public compiler on MT6989; fp16 is what
  transcribed word-perfect). Chunked encoders, 512/832-position graphs, JIT compilation on device: none of it.
  The measured artefacts are the product artefacts.

## 2. The pieces

### 2.1 Census: a vendor per family

`NpuSocFamily` (`npu/NpuFleetCensus.kt`) gains

```kotlin
enum class NpuVendor { QUALCOMM, MEDIATEK }
val vendor: NpuVendor
val manufacturers: Set<String>      // the Build.SOC_MANUFACTURER spellings that match this family
val runtime: NpuRuntimeNeeds        // sealed: Qnn(skelAsset, skelBytes, skelSha256, htpVersion) | LiteRtMediatek(neuronMajor = 8)
```

The five Qualcomm families keep `manufacturers = setOf("QTI", "Qualcomm")` (the set `NpuGate` holds today, moved
onto the rows) and their skel triples inside `Qnn(...)`; `htpVersion` moves with them. Two new rows:

| id | packGroup | socModels | manufacturers | runtime | evidence |
|---|---|---|---|---|---|
| `mt6989` | `soc_mt6989` | `{"MT6989"}` | `{"Mediatek"}` | `LiteRtMediatek(neuronMajor = 8)` | Tab S10+ E0 read (`ro.soc.manufacturer=Mediatek`, `ro.soc.model=MT6989`), Play catalog 24 rows "Mediatek MT6989"; t2–t6 on the owner's SM-X828U |
| `mt6991` | `soc_mt6991` | `{"MT6991"}` | `{"Mediatek"}` | `LiteRtMediatek(neuronMajor = 8)` | Play catalog rows for Tab S11/S11 Ultra "Mediatek MT6991"; compiled 2026-09-24, NOT device-executed (Samsung RTL pending) |

`PackArtifact` rows for `(npu-turbo, mt6989)` and `(npu-turbo, mt6991)` carry the AOT files' exact lengths and
sha256 (encoder 1,302,606,488 B; decoder 584,862,184 B for MT6989; the MT6991 pair measured the same way).
`vendorZipBytes` becomes `sourceBytes` with a documented meaning per vendor: the vendor zip for Qualcomm, our
delivery file for MediaTek (maintenance rule 2 is amended: "a vendor package OR a recorded self-compile with
its build recipe in `tools/mtk-apu/`"). The Play device-group renderer emits the family's own manufacturer, so
`device_targeting_config.xml` gains
`<config:device-group name="soc_mt6989"><config:device-selector><config:system-on-chip manufacturer="Mediatek" model="MT6989"/>…`
(and `soc_mt6991`), regenerated byte-for-byte by `NpuPackLayoutTest` as today.

### 2.2 Gate: the family decides its manufacturer

`NpuGate.familyFor(socModel, socManufacturer)` stops consulting one global manufacturer set and asks the row:
`family.manufacturers.contains(manufacturer)`. `SUPPORTED_SOC_MANUFACTURERS` survives as the union, derived, for
the tests that quote it. The capability half (`WhisperEverywhereApp.npuCapableDevice`) becomes vendor-dispatched:
Qualcomm keeps its QNN dlopen probe; MediaTek calls the driver check of §2.3. `offeredNpuTierIds()` and
`pickableFor` are untouched: the routing set is still `{npu, npu-turbo}` and `ONE_TIER_ID` is still turbo. A
MediaTek family simply has no `npu` artifact row, so the small tier is not offered there.

### 2.3 The driver check (owner ruling)

Why: LiteRT's MediaTek dispatch loads the Neuron driver by trying names in order — in v2.1.1
`libneuronusdk_adapter.mtk.so`, then `libneuronusdk_adapter.9.mtk.so` (only if a "magic number" read from
`libneuron_sys_util.mtk.so` says the ROM is v9-class), then `libneuron_adapter_mgvi.so`, then a
`libneuron_adapter.so` — and its loop has no `break` (`neuron_adapter_api.cc` v2.1.1 lines 109-116, read
2026-09-24): every name that loads overwrites the previous, so **the last loadable adapter wins**, in v2.1.1 as
much as on main (#9364). The bytecode we ship was produced by NeuroPilot 8.2.30 and the dispatch restores it only
on a Neuron runtime of the same major. On the Tab S10+ only the first name loads and it reports 8.2.26. Elsewhere
it could be absent (a ROM that never whitelisted it), a different major, or shadowed by a later candidate.

Our manifest declares exactly one adapter name (§2.3, last paragraph), so in the app's linker namespace only
that name can load and the loop's outcome is deterministic. The check below still walks the same list, so it
answers what LiteRT would bind rather than what we hope it binds.

What: `nativeProbe(libDir)` in the new engine, run by `npuCapableDevice` before any model file is opened:

1. Walk LiteRT's candidate list in LiteRT's order (`libneuronusdk_adapter.mtk.so`, `libneuronusdk_adapter.9.mtk.so`,
   `libneuron_adapter_mgvi.so`, `libneuron_adapter.so`), `dlopen` each, and keep the LAST that loads — the one
   LiteRT will bind. None loads → `refuse(adapter-missing)`. The winner is not `libneuronusdk_adapter.mtk.so` →
   `refuse(adapter-<name>)`: a different driver than the one the tier was measured on is not admitted by
   inference.
2. `dlsym("Neuron_getVersion")` (`NeuronAdapter.h:888`, `int Neuron_getVersion(NeuronRuntimeVersion*)`) →
   `{major, minor, patch}`; `major != family.runtime.neuronMajor` → `refuse(driver-major-<got>-want-<want>)`.
3. Read the bytecode's stamp from our own pack metadata (`compiler = "adapter 8.2.30"`, written at build time
   from the file) and assert its major equals the driver's. Two sources, one fact.
4. Report the line `apu: driver=usdk.mtk <major.minor.patch> want=<major> pass` (or the refusal) through the
   same diag channel the QNN probe uses, so the tier-status card and the log readers see it.

The manifest declares `<uses-native-library android:name="libneuronusdk_adapter.mtk.so" android:required="false"/>`
and nothing else from the MediaTek set: not `libneuron_sys_util.mtk.so` (so the `.9` candidate is never
considered, which is right for v8 bytecode), not `libneuron_adapter_mgvi.so`. A refusal is the existing loud CPU
fallback (`fallBackToCpuTier`), never a silent one.

**The 5 s cold-start wait is NOT the magic-number read (P0, measured 2026-09-24, run `t7_p0_nosysutil_enc_aot_npu`):**
with `libneuron_sys_util.mtk.so` undeclared, `create` was still 8,457 ms with exactly one
`Waiting for service 'vendor.mediatek.hardware.neuropilot.neuronservice.INeuronService/default'` line, and the
timestamps place the wait INSIDE `dlopen("libneuronusdk_adapter.mtk.so")` — after the dispatch library loads and
before LiteRT logs which adapter it bound. The adapter's own initialisation tries the (unregistered) Neuron
service for 5 s, logs `Faild to get neuron serivce`, and falls back to the `apuware` AIDL path that then works.
So the wait is MediaTek's, paid once per process on the first adapter instantiation (the second model paid 0.9 s
in t6). The design's answer is to pay it where nobody waits: the engine's `warmUp()` — `dlopen` of the adapter
through a trivial `LiteRtCreateEnvironment` + dispatch initialisation — runs on the service's boot prewarm
thread outside `NativeComputeGate`, so by the time a user arms the tier the 5 s is already spent. A cold tap
before prewarm finishes still pays it inside the StartupRing's 6 s budget (5.0 + 1.3 s restore + 0.9 s = 7.2 s
worst case, over budget by 1.2 s): the ring copy covers that once ("the AI chip is waking up"), and the sheet
records how often it happens in a 30-minute session.

### 2.4 The engine seam

Today `NpuWhisperBackend` (`transcription/NpuWhisperBackend.kt`, ~1,150 lines) holds the tier's policy — stage
order, epoch/session guards, the loud fallback, sentence slots, language resolution, diag — and talks to
`QnnAsrNative` directly. The policy must not fork. So:

```kotlin
interface NpuAsrEngine {
    fun probe(libDir: String): String
    fun init(spec: NpuModelSpec, files: NpuEngineFiles, libDir: String): String   // "" on success, else the refusal
    fun inputQuant(): FloatArray?          // QNN: the ufixed16 mel scale/offset; LiteRT: null (float mel)
    fun encode(mel: FloatArray): String     // fills the cross-KV inside native memory
    fun decodeSegment(...): Int             // the same contract nativeDecodeSegment has today
    fun detectLanguage(): Int
    fun epoch(): Long; fun release(epoch: Long); fun lastError(): String; fun setDiag(on: Boolean)
}
```

`QnnAsrEngine` wraps `QnnAsrNative` unchanged (the skel staging stays a Qualcomm-only step inside its `init`).
`LiteRtAsrEngine` wraps the new `LiteRtAsrNative`. `NpuWhisperBackend` takes the engine from
`NpuBackendSelector.backendFor` by `family.vendor`, and the only vendor-shaped lines left in it are the mel
handoff (`inputQuant() == null` → pass the float mel) and the engine choice. The source pins that quote
`QnnAsrNative` symbols inside the backend (`NpuNativeContractTest` and friends) are re-specced in the same
commit as the extraction; that is the price of one policy body, paid once.

### 2.5 `liblitertasr.so` — the native engine

A third `add_library` in `app/src/main/cpp/CMakeLists.txt` beside `whisper_jni` and `qnnasr`, built against the
LiteRT **2.1.1** C headers (`litert_cc_sdk.zip` from the v2.1.1 release, vendored under
`app/src/main/cpp/third_party/litert-2.1.1/`), linking only `log` and `dl`. Like `qnnasr`, it reaches every
runtime entry point through `dlopen`/`dlsym` of `libLiteRt.so` from `nativeLibraryDir`, so the library loads on
every device and the runtime's absence is a probe result, not a linker crash.

Entry points used: `LiteRtCreateEnvironment` with `kLiteRtEnvOptionTagDispatchLibraryDir` = the staged dispatch
directory (§2.6); `LiteRtCreateModelFromFile` ×2; `LiteRtCreateOptions` + `LiteRtSetOptionsHardwareAccelerators(NPU)`
(NPU only — a refusal is an error, never a silent CPU run) + the MediaTek options (performance mode
`kLiteRtMediatekPerformanceModeHigh`, to be measured against default in P0); `LiteRtCreateCompiledModel` ×2;
`LiteRtCreateTensorBufferFromHostMemory` for every input and output; `LiteRtRunCompiledModel`.

Buffers, all host memory the engine owns: the mel `[1,128,3000]` f32; the eight cross-KV tensors
(`[20,1,64,1500]`/`[20,1,1500,64]`, 61 MB total) shared between the encoder's outputs and the decoder's inputs
without a copy; **two** sets of self-cache buffers (`[20,1,64,199]`/`[20,1,199,64]` × 4 layers, 8 MB per set) used
ping-pong — step *t* reads set A and writes set B, step *t+1* reads B and writes A — so the 9.9 ms per token the
probe spent copying caches in Kotlin becomes zero; `input_ids` i32, `position_ids` i32, `attention_mask`
f32[1,1,1,200] (additive, −1e4 beyond the live window, the fp16-safe value that transcribed correctly);
`logits` f32[1,51866,1,1]. The 24 embedding-lookup ops the compiler left on the CPU run inside LiteRT's
interpreter in front of the dispatch; they cost nothing measurable and need no code.

The decode loop is the QNN loop's algorithm (`qnn_asr.cpp:3051-3503`: prompt, greedy step, timestamp tokens,
the sentence/geometry bookkeeping, EOT, the 199-slot window) over float logits instead of ufixed16 — ported into
a header shared by both engines (`asr_decode_loop.h`, templated on the logits accessor), so the two vendors run
the same loop rather than two copies of it. `NpuNativeContractTest`'s pins on the loop move to the header.

### 2.6 Runtime packaging

- `libLiteRt.so` (2.1.1, 5,104,832 B, sha256 `6ddc1b3df38f3f0e039558c023f3bd9ec2f7bec55b67cfd6be4131130481a5d5`,
  from `com.google.ai.edge.litert:litert:2.1.1` on Google Maven, AAR 7,569,479 B) ships in `lib/arm64-v8a/` of the base module. It is extracted from the
  `com.google.ai.edge.litert:litert:2.1.1` AAR by a `litertRuntime` Gradle configuration with a sha256 pin, the
  way `qnnSkelSource` extracts the QNN skels — the app never takes the AAR's Kotlin API or its transitive
  dependencies (coroutines-guava, lifecycle, guava, play-ai-delivery), which is why the C API is the seam.
- `libLiteRtDispatch_MediaTek.so` (v2.1.1, 409,728 B, sha256 `9e963c56a65b6146b0e94aed82dd0f73dbaee6805fc6ae090580565b57680706`,
  the only MediaTek dispatch Google has published) ships as an APK asset and is staged into
  `filesDir/litert_dispatch/` by `NpuAssetStage.stageWithMarker`, because LiteRT scans the dispatch directory
  with `std::filesystem` and the app's `extractNativeLibs=false` keeps `lib/` inside the APK. Its version is
  pinned by the same marker+digest scheme as the skels.
- No compiler plugin, no OpenCL accelerator, no LiteRT-LM: the artefacts are precompiled and the CPU kernels are
  inside `libLiteRt.so`.
- The runtime is pinned at 2.1.1 until a MediaTek dispatch exists for a newer LiteRT. Building the dispatch
  from source (documented, Bazel on the MS-02) is the upgrade path and is out of this design's scope.

### 2.7 Packs and delivery

The pair is 1.88 GB and a Play asset pack holds 1.5 GB, so the MediaTek pair is split across two on-demand
packs by device group:

- `npu_turbo` gains device groups `soc_mt6989` and `soc_mt6991` carrying **the encoder only**
  (`turbo_encoder_mtk.tflite`, 1.30 GB each) plus `metadata.json`.
- A new asset-pack module `npu_turbo_tail` (on-demand) carries **the decoder** (`turbo_decoder_mtk.tflite`,
  0.58 GB) for the same two groups and nothing for Qualcomm groups. The Play fetch step requests both packs for
  a MediaTek family and treats the pair as one artifact (both present and digest-verified, or the tier is not
  installed); the SAF import path accepts the two delivery names and checks the same digests.
- `metadata.json` moves to version 2: `vendor` (`"qualcomm"` | `"mediatek"`), `compiler` (the QAIRT string, or
  `"adapter 8.2.30"` read from the bytecode's embedded record), `htpVersion` optional, `neuronMajor` optional,
  entries as today. Version-1 files (every shipped Qualcomm pack) keep parsing.
- `tools/build_asset_packs.py` gains a `LOCAL` family source: the artefact directory
  (`~/mtk-whisper/out/pair/aot_mt6989/`, `aot_mt6991/`), digests+lengths pinned in `CENSUS` like vendor rows, the
  build recipe referenced (`tools/mtk-apu/README.md`), the compiler stamp read from the file and written to the
  metadata. `verifyNpuPacks` learns the tail module and the vendor field.
- AAB: +3.76 GB for the two MediaTek families (≈ 11.5 GB with workstream A's 7.8 GB); per-pack ≤ 1.5 GB and the
  30 GB on-demand budget hold. A Tab S10+ downloads 1.88 GB.

### 2.8 Card, copy, status

The turbo card is vendor-neutral already ("the AI chip"); `NpuTierStatus.cardNote` and the offer line print
`soc=MT6989:pass` from the family. `ModelTierCopy` gets no new strings unless a reviewer finds a Qualcomm word in
the turbo copy. HowToGuide: one sentence naming the Galaxy Tab S10/S11 among the AI-chip devices.

### 2.9 Cadence and calibration

The cadence row bills `encode + tokens × per-token` per commit. The MediaTek family's constants come from the
device directly (encode 1,783 ms, 22.8 ms/token from t6; re-measured in-app at P3), not from an AI Hub→device
calibration. The 8 s floor and the S23 precedent make the Tab S10+ an admitted device at 2.24 s per 20-token
commit; the first in-app session measures the sustained value.

## 3. A commit, end to end

1. The service's mel path (whisper.cpp's, with the bundled 128-bin bank — unchanged) produces the float mel.
2. `NpuWhisperBackend.transcribe` → `engine.encode(mel)`: `LiteRtRunCompiledModel(encoder)` fills the eight
   cross-KV buffers in place (1.78 s on the APU).
3. `engine.decodeSegment(...)`: the shared loop runs the decoder step per token (23 ms), ping-ponging the caches,
   returning the same token/timestamp/sentence structures the QNN engine returns.
4. Everything after — sentence slots, speakers, the bubble — is the code that runs today.

## 4. Failure modes

| Failure | Where it is caught | What the user sees |
|---|---|---|
| Driver absent / wrong major | §2.3 probe, before any file is opened | tier not offered; card says why (`apu: driver-major-9-want-8`) |
| Bytecode restore refused by the runtime | `init` (LiteRtCreateCompiledModel error) | loud CPU fallback, diag line, the tier-status card |
| Pack pair incomplete or digest mismatch | pack fetch / SAF import | tier not installed; existing copy |
| NPU-only compile refused at runtime (accelerator missing) | `init` | loud CPU fallback |
| OOM while both models resident | `init`/`encode` error path | loud CPU fallback; trim re-arm as today |
| The 5 s adapter-init wait (P0: present, and MediaTek's, not LiteRT's) | `warmUp()` on the boot prewarm thread | nothing, unless the user arms within ~7 s of the process starting: then the ring's "waking up" copy once |

## 5. Testing and acceptance

- JVM pins: census (7 families, vendor per row, the MediaTek rows' digests), gate (Mediatek/MT6989 → mt6989;
  `MediaTek`/`mediatek` spellings refused until a device reports them; QTI unchanged), layout (the two new device
  groups; the tail module; byte-identical XML), metadata v2 round-trip and v1 compatibility, selector (vendor →
  engine), packaging (libLiteRt in lib/, the dispatch as an asset with its digest, the manifest's native-library
  set with `libneuron_sys_util` absent), release identity.
- Native: `liblitertasr.so` builds on the MS-02 and the PC; a host-side unit of the shared decode loop against a
  recorded logits trace (the probe's t6 run exports one) so the port is checked before the device.
- Device (owner, Tab S10+ via the internal track — a local build cannot install over the sideload/Play copy):
  the offer line `soc=MT6989:pass`, the driver line, zero or one `Waiting for service` lines, cold-arm time,
  per-commit encode+decode against t6, canary + jfk transcripts equal to t6's, a 30-minute session with thermal
  status, PSS. That sheet is the ship gate.
- Tab S11 (MT6991): a Samsung Remote Test Lab session with the probe APK and the MT6991 pair before the family is
  marked device-executed; until then its evidence string says "compiled, not executed".

## 6. Phases

- **P0 — probe runs on the tablet:** (a) DONE 2026-09-24: without `libneuron_sys_util.mtk.so` declared,
  `create` stayed at 8,457 ms with the one 5 s wait — the wait is inside the adapter's own init (§2.3), so the
  lever is the boot-prewarm `warmUp()`, not the manifest. (b) MediaTek performance mode high vs default: not
  reachable from the probe's Kotlin API (2.1.1 exposes no MediaTek options class); measured in P1 through the
  C API, on the first engine build.
- **P1 — engine (3–4 days):** `asr_decode_loop.h` extraction + `liblitertasr.so` + `LiteRtAsrNative` +
  `NpuAsrEngine` + `NpuWhisperBackend` on the seam; pins re-specced; JVM suite green; the native loop's host test.
- **P2 — census, gate, packs (2 days):** §2.1–2.3, §2.6–2.7; `build_asset_packs.py` LOCAL source; the tail module;
  metadata v2; layout/packaging pins; AAB built and size-verified on the MS-02.
- **P3 — ship (1 day + owner sessions):** copy/status, version bump, internal track, the Tab S10+ sheet; then the
  RTL session for MT6991.

P1 and P2 are independent until P2's selector wiring, so they can run in parallel worktrees. All of B rebases on
workstream A (`feat/qnn-250-8gen1`) because both touch the census; B's branch is `feat/mediatek-apu-tier`.

## 7. Open questions

1. Spelling: the tablet and the Play catalog say `Mediatek`; LiteRT's enum says `MediaTek`. The row admits only
   what a device reports (`Mediatek`), per census rule 1; a second spelling is added only with a device read.
2. Whether Google publishes a MediaTek dispatch for a newer LiteRT (licence talks, #9482). If it does, the
   runtime pin moves; nothing in this design changes shape.
3. MT6991 restore and speed are unmeasured (no device). The family ships only after an RTL run, or the owner
   rules on compiled-only evidence as for the 8 Elite plains.
